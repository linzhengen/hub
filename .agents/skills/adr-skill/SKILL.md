# hub ADR 規範

## 目的

ADR は **エージェントが実装できる仕様**である。人が判断を承認し、エージェントが
それを実装する。追加の質問なしにコードを書けるだけの情報が ADR に入っていなければ、
ADR としては未完成である。

hub のコードベースには既に強い書き方の規律がある。ADR もそれに従う。

- **なぜそうしたかを書く。**何をしたかはコードが語る。ADR が持つのは理由の方である。
- **規則は 1 か所にだけ書く。**同じ規則が 2 か所にあれば、2 か所で食い違う。
  ADR に書いた規則は、コード側では 1 つの関数・1 つのマップ・1 つの列に落ちるはずで、
  落ちないなら判断がまだ具体的になっていない。
- **却下した案とその理由を書く。**後から「なぜ素直な方をやらなかったのか」を
  訊かれるのは必ず起きる。
- **検証手順を具体的なコマンドで書く。**「動くこと」は検証条件ではない。

## どこに書くか

hub には目的の違う 3 つの置き場がある。**新しい置き場を増やさないこと。**

| 置き場 | 何を持つか | 粒度 |
|:--|:--|:--|
| `docs/design/` | 方向性メモ。複数の判断をまたぐ物語と、その前提となる現状分析 | 大きい・長寿命 |
| `docs/decisions/` | **ADR。1 ファイル 1 判断** | 1 判断 |
| `docs/tasks/` | 残タスク。PR 1 本ぶんの作業手順 | 1 PR |

判断に迷ったら:

- 「この領域をこれからどうしていくか」= 方向性メモ
- 「A ではなく B にする。理由は〜」= **ADR**
- 「次に何をするか」= タスク

方向性メモの中の「設計判断 N」が、後から争点になる・覆すのが高くつくと分かった時点で、
ADR に**昇格**させる。メモ側からはその ADR にリンクし、判断の本体は ADR に移す。
両方に本体を置かないこと。

`docs/build.mjs` は `docs/site/` しか読まないので、`docs/decisions/` は
公開サイトに含まれない。社外に出したくない判断も書いてよい。

## ADR を書くとき / 書かないとき

書く:

- **システムの作り方や運用を変える**（新しい依存、アーキテクチャの型、API 規約、インフラ選択）
- **コードが乗ってしまうと戻しづらい**
- **後から来る人やエージェントに影響する**
- **本当に選択肢があった**（比較して落とした案がある）

書かない:

- 既存の型の中での普通の実装判断
- バグ修正・誤字修正
- 既存 ADR で決まっていること（新規に書かず、その ADR を更新する）
- linter / formatter が既に強制しているスタイル

迷ったら: 後から来るエージェントが**理由**を知って得をするなら、書く。

### hub 固有の「止まって ADR を提案する」条件

エージェントとしてこのリポジトリで作業していて次に当たったら、**手を止めて ADR を提案する**。
いずれも hub が明示的に守っている不変条件に触れる操作である。

- **proto を単一の出所から外そうとしている。** REST パスやパーミッションを手で書く、
  `pkg/apicatalog` を経由しない経路を足す、生成物を手で直す。
- **認可判定が読む新しいテーブルを足そうとしている。**`rbac_revisions` トリガが要る
  （`server/AGENTS.md` §11）。トリガを付けない判断をするなら、それは ADR 案件である。
- **判定とキャッシュの不変条件に触れようとしている。**「キャッシュはポリシーの集合を持ち、
  判定結果は持たない」を崩す変更（SQL 側でのフィルタ追加など）。
- **認証経路または認可経路を 2 本にしようとしている。**`service_accounts` が
  「第二の主体種別を作らない」と決めた線を越える変更。
- **`toolbox.go` の `escalation` / `exposed` を緩めようとしている。**
- **監査の `audited` / `notAudited` の分類方針そのものを変えようとしている。**
- **マイグレーションを新規に足すか、既存を直すかで迷っている。**このリポジトリは
  既存マイグレーションの修正を許しているが、それは判断であって既定ではない。
- **新しい依存やクラウドプロバイダを持ち込もうとしている。**`infra/tf` には現状
  クラウドプロバイダが 1 つも無く、backend は `local {}` である。
- **「なぜ」を説明する長いコードコメントを書き始めている。**その理由は ADR に属する。

**提案の仕方**: どの判断に当たったか、なぜそれが重要かを人に伝え、ADR にするか訊く。
する場合は下の 4 フェーズを回す。しない場合はコードコメントに残して先に進む。

## ADR の作成: 4 フェーズ

フェーズを飛ばさないこと。

### フェーズ 0: リポジトリを読む

質問する前に文脈を集める。

1. **既存 ADR を読む。**`docs/decisions/` と索引 (`README.md`)。
   関連する判断、これが置き換えることになる判断、既存の規約を控える。
2. **方向性メモを読む。**`docs/design/`。特に「今回は扱わないもの」の節は、
   その判断が**意図的に先送りされたもの**かどうかを教えてくれる。
3. **規約を読む。**`server/AGENTS.md`（特に §11 認証・認可、§13 実装規約、§17 API 規約）、
   `ui/web/AGENTS.md`、`infra/*/AGENTS.md`。判断が既存の規約と矛盾していないか確かめる。
4. **技術スタックを見る。**`go.mod`、`ui/web/package.json`、`infra/tf`。
5. **関係するコードを読む。**判断が触る領域の実装と、既にある型を特定する。
6. **コード中の ADR 参照を探す。**どの判断がどの領域を支配しているかが分かる。

### フェーズ 1: 意図を捉える（ソクラテス式）

**一度に 1 問ずつ**訊く。質問リストを丸ごと投げないこと。前の答えを踏まえて次を訊く。
フェーズ 0 で分かっていることは飛ばす。

1. **何を決めるのか** — 短く具体的な題。動詞句にする（「X を採用する」「Y を Z に置き換える」）。
2. **なぜ今か** — 何が壊れたか、何が変わるか、放置すると何が壊れるか。
3. **制約は何か** — 既存コード、規約、スタック、期限。フェーズ 0 で見たものを当てる
   （「`service_accounts` が既に主体の形を決めていますが、これは制約になりますか」）。
4. **成功とは何か** — 測れる形まで押す。
5. **どの選択肢を検討したか** — 最低 2 つ。1 つしか無いなら、なぜ他が落ちたのかを一緒に言語化する。
6. **今の傾きは** — 直感を先に捉える。言語化されていない優先順位が出てくる。
7. **誰が承認するか / 誰に伝わる必要があるか**
8. **エージェントが実装するのに何が要るか** — どのファイル、どの既存の型に倣うか、
   何を避けるか、どのテストで確かめるか。これが実装計画になる。

追加で効く問い:

- 「この判断が間違っていた場合、最悪どうなりますか」
- 「半年後に見直すとしたら、何が起きたときですか」
- 「明示的にやらないと決めていることはありますか」
- 「`docs/design/` の〈メモ〉がこの領域を扱っていますが、それとの関係は」

**やめどき**: 実装計画を含む全節を、でっち上げずに埋められるようになったら。
どこかを推測しているなら、まだ訊く。

**意図サマリの関門**: フェーズ 2 に進む前に、捉えた内容を提示して確認を取る。

> **ADR に記録する内容:**
>
> - **題**: {title}
> - **きっかけ**: {なぜ今}
> - **制約**: {list}
> - **選択肢**: {A} / {B}
> - **傾き**: {どれを、なぜ}
> - **やらないこと**: {非目標}
> - **関連する ADR / メモ / コード**: {既存の何と噛み合うか}
> - **影響範囲**: {どのファイル・領域}
> - **検証**: {どうやって実装できたと判断するか}
>
> **この理解で合っていますか。足すもの・直すものはありますか。**

確認が取れるまでフェーズ 2 に進まない。

### フェーズ 2: 起草する

1. **置き場**: `docs/decisions/`。無ければ作る。
2. **ファイル名**: `YYYY-MM-DD-english-slug.md`。**ファイル名は英語スラグ、本文は日本語。**
   `docs/design/` と同じ流儀（`iga-direction.md` / 本文は日本語）。
3. **テンプレート**:
   - `assets/templates/adr-simple.md` — 素直な判断（勝者が明らかで、比較が短い）
   - `assets/templates/adr-madr.md` — 選択肢が 3 つ以上、構造化した比較を残したい
   - 迷ったら simple。`references/template-variants.md` を参照。
4. **全節を埋める。**プレースホルダを残さない。任意の節は、使わないなら消す。
5. **実装計画を書く。**エージェント向け ADR で最も重要な節。
6. **検証をチェックボックスで書く。**`make test` / `golangci-lint run ./...` /
   `pnpm test` など、**実際に走るコマンド**で書く。
7. **ファイルを作る。**`scripts/new_adr.js` を使う。使えない場合はテンプレートを手で写す。

### フェーズ 3: チェックリストで見直す

`references/review-checklist.md` に照らす。**生のチェックリストを貼らず、要約で示す。**

> **ADR レビュー**
>
> ✅ **問題なし**: {堅い点}
>
> ⚠️ **不足**:
>
> - {具体的な不足 1}
> - {具体的な不足 2}
>
> **判断**: {出せる / 先に埋める / フェーズ 1 に戻る}

不足があれば、指摘だけでなく直し方を提案して承認を求める。
チェックリストを通るか、人が明示的に不足を受け入れるまで確定しない。

## ADR を参照する（読む側の手順）

ADR がある領域に手を入れる前に読む。これは作成フローとは独立した操作である。

1. `docs/decisions/` と索引を見る。`accepted` のものが生きている判断。
2. 題だけでなく、文脈・判断・帰結・非目標・**実装計画**まで読む。
   実装計画がどの型に倣うべきかを書いている。
3. **判断を尊重する。**`accepted` な ADR に反することをするなら、それを置き換える
   新しい ADR が要る。コードと ADR が食い違っていたら人に報告する。
4. PR とコードコメントから ADR を参照する（下記）。

読むべき時:

- アーキテクチャに触れる作業を始める前（認可、データ層、API 設計、インフラ）
- コードの型を見て「なぜこうなっているのか」と思ったとき
- 既存の判断と衝突しそうな提案をする前
- 人が「ADR を見て」と言ったとき

## コードと ADR の相互リンク

### ADR → コード

実装計画に具体的なパスと型を書く。

```markdown
## 実装計画

- **影響範囲**: `server/internal/domain/auth/`, `server/internal/interface/grpc/interceptor/`
- **倣う型**: 期限付き付与と同じ、判定時に落とす形（`auth.Service.Enforce`）
```

### コード → ADR

その判断に導かれて書いたコードの入り口に、1 か所だけコメントを置く。行ごとには書かない。

```go
// 委譲は DB の行であってトークンではない。認可経路を 2 本にしないための判断。
// ADR: docs/decisions/2026-09-10-delegation-as-a-database-fact.md
type Delegation struct {
```

```typescript
// 組織は判定時に落とす。SQL でフィルタするとキャッシュの不変条件が壊れる。
// ADR: docs/decisions/2026-09-04-scope-a-permission-to-an-organization.md
```

## その他の操作

### 既存 ADR の更新

- **受理 / 却下**: status を変える。
- **非推奨化**: status → `deprecated`、代替の経路を書く。
- **置き換え**: 新しい ADR を作り、**双方向にリンク**する（旧 → 新、新 → 旧）。
- **学びの追記**: `## 補足` に日付付きで足す。**過去を書き換えない。**

status の変更は `scripts/set_adr_status.js` を使う。

### 受理後

1. **実装計画と帰結の項目をタスクにする。**`docs/tasks/` か GitHub Issue。
2. **PR から参照する。**PR 本文に ADR のパスを書く（`create-pr` skill の
   「変更の背景と解決策」に入れる）。
3. **コードに参照コメントを置く。**
4. **検証項目を実際に走らせ、結果を `## 補足` に日付付きで残す。**
5. **見直し条件を監視する。**ADR が「X が起きたら再考」と書いているなら、それを見る。

### 索引

`docs/decisions/README.md` を最新に保つ。`scripts/new_adr.js --update-index` が更新する。

### 立ち上げ

`docs/decisions/` がまだ無いとき:

```bash
node .agents/skills/adr-skill/scripts/bootstrap_adr.js
```

ディレクトリ、索引、最初の ADR（「ADR を採用する」）を作る。

## リソース

### scripts/

- `scripts/new_adr.js` — テンプレートから ADR を作る
- `scripts/set_adr_status.js` — status を書き換える（`--json` で機械可読出力）
- `scripts/bootstrap_adr.js` — ディレクトリ・索引・最初の ADR を作る

### references/

- `references/review-checklist.md` — フェーズ 3 のチェックリスト
- `references/adr-conventions.md` — 置き場・ファイル名・status・寿命の規約
- `references/template-variants.md` — simple と MADR の使い分け
- `references/examples.md` — hub の実際の判断で書いた記入例

### assets/

- `assets/templates/adr-simple.md` — 素直な判断向け
- `assets/templates/adr-madr.md` — 選択肢が多い判断向け（MADR 4.0 準拠）
- `assets/templates/adr-readme.md` — 索引の雛形

### コマンド例

リポジトリのルートから:

```bash
# 素直な判断
node .agents/skills/adr-skill/scripts/new_adr.js --title "Scope a permission to an organization"

# 選択肢が多い判断
node .agents/skills/adr-skill/scripts/new_adr.js --title "Choose an agent runtime" --template madr

# 索引も更新する
node .agents/skills/adr-skill/scripts/new_adr.js --title "..." --update-index

# 受理する
node .agents/skills/adr-skill/scripts/set_adr_status.js docs/decisions/2026-09-04-....md --status accepted
```

**題は英語**（ファイル名スラグになる）。**本文は日本語**。
