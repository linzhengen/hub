# hub ADR 規範

## 目的

ADR は **エージェントが実装できる仕様**である。人が判断を承認し、エージェントが
それを実装する。追加の質問なしにコードを書けるだけの情報が入っていなければ、未完成である。

hub のコードベースには既に強い規律がある。ADR もそれに従う。

- **なぜそうしたかを書く。**何をしたかはコードが語る。ADR が持つのは理由の方である。
- **規則は 1 か所にだけ書く。**同じ規則が 2 か所にあれば、2 か所で食い違う。
  ADR に書いた規則は、コード側では 1 つの関数・1 つのマップ・1 つの列に落ちるはずで、
  落ちないなら判断がまだ具体的になっていない。
- **却下した案とその理由を書く。**「なぜ素直な方をやらなかったのか」は必ず後から訊かれる。
- **検証は実際に走るコマンドで書く。**「動くこと」は検証条件ではない。

## どこに書くか

hub には目的の違う 3 つの置き場がある。**新しい置き場を増やさないこと。**

| 置き場 | 何を持つか | 粒度 |
|:--|:--|:--|
| `docs/design/` | 方向性メモ。複数の判断をまたぐ物語と、その前提となる現状分析 | 大きい・長寿命 |
| `docs/decisions/` | **ADR。1 ファイル 1 判断** | 1 判断 |
| `docs/tasks/` | 残タスク。PR 1 本ぶんの作業手順 | 1 PR |

- 「この領域をこれからどうしていくか」= 方向性メモ
- 「A ではなく B にする。理由は〜」= **ADR**
- 「次に何をするか」= タスク

方向性メモの中の判断が争点になった、または覆すのが高くつくと分かったら、ADR に**昇格**させる。
メモからは ADR にリンクし、**判断の本体は片方にだけ置く。**

`docs/build.mjs` は `docs/site/` しか読まないので、`docs/decisions/` は公開されない。

## いつ書くか

### A. 会話で方針が決まった直後 ← **最も取り逃がしやすい**

hub の判断の多くは、コードに触る前ではなく**人の一言**で決まる。
「既存のマイグレーションを修正して OK」「このまま PR に含める」「それは書かないで」。
これらは発言された瞬間に決着し、どこにも残らず、次に来たエージェントが
**なぜそうなっているかを再発見する羽目になる。**

次のいずれかが起きたら、**その場で記録するかを確かめる**。

- 人が**既定・慣行・以前の判断を覆した**（「〜で OK」「〜しなくていい」「〜は要らない」）
- 人が**提示した選択肢から選んだ**（選ばれなかった案の理由が、この瞬間にしか残らない）
- 人が**エージェントの提案を却下した**（却下の理由が最も失われやすい）
- **同じ論点が 2 回目に出てきた**（1 回目が記録されていない証拠）
- 人が**ツールや外部の既定より、この repo の流儀を優先した**

**作業を中断しないこと。**その場で長い聞き取りを始めると、人が本来やろうとしていた
作業が止まる。手順はこう:

1. **一行だけ確認する** ——「これは ADR に残す判断ですか」
2. **今のタスクを終える**
3. **区切りで `brief` テンプレートの下書きを出す。**会話に答えは出揃っているので、
   聞き取りは要らない。埋まらない欄があるときだけ訊く

`brief` は 4 節しかない: 何が既定だったか / 何をどう決めたか / 何が変わるか / いつ見直すか。
**「何が既定だったか」が空なら、ADR は要らない** —— 既定どおりのことをしただけである。

### B. コードに触れる前

次に当たったら、**手を止めて ADR を提案する**。いずれも hub が明示的に
守っている不変条件に触れる操作である。

**server / 認可**

- proto を単一の出所から外そうとしている（REST パスやパーミッションを手で書く、
  `pkg/apicatalog` を経由しない経路、生成物の手直し）
- 認可判定が読む新しいテーブルを足そうとしている（`rbac_revisions` トリガが要る。
  `server/AGENTS.md` §11）
- 「キャッシュはポリシーの集合を持ち、判定結果は持たない」を崩そうとしている
  （ポリシークエリへのフィルタ追加など）
- 認証経路または認可経路を 2 本にしようとしている（`service_accounts` が引いた線）
- `toolbox.go` の `escalation` / `exposed` を緩めようとしている
- 監査の `audited` / `notAudited` の分類方針そのものを変えようとしている
- マイグレーションを新規に足すか既存を直すかで迷っている

**ui/web**

- `src/api/operations.ts` を経由せず REST パスやクエリ文字列を手で書こうとしている
  （server 側の「proto を単一の出所に」と同じ規律の web 版）
- `Markdown.tsx` の安全側の既定を緩めようとしている（`rehype-raw` の追加など）。
  ツール結果には他人が書いた文字列が混ざるので、これは `escalation` と同格の判断である
- React Compiler のルールを緩めて違反を黙らせようとしている
- 3 つ目の UI ライブラリを足そうとしている（Ant Design と Shadcn が既に同居している）
- 認証トークンやそれに準ずるものを `localStorage` に置こうとしている

**infra / リリース**

- 新しいクラウドプロバイダを持ち込もうとしている（`infra/tf` には現状 1 つも無く、
  backend は `local {}`）
- Terraform の state の置き場を変えようとしている
- 新しい依存・チャート・ベースイメージを足そうとしている

**ドキュメント**

- 公開サイト（`docs/site/`）に何を載せるかの方針を変えようとしている
- 生成物（API リファレンス、OpenAPI）を手で直そうとしている

**共通**

- 「なぜ」を説明する長いコードコメントを書き始めている。その理由は ADR に属する

### 書かないもの

- 既存の型の中での普通の実装判断
- バグ修正・誤字修正
- 既存 ADR で決まっていること（新規に書かず、その ADR を更新する）
- linter / formatter が既に強制しているスタイル

## 大きさの目安

**ADR は短いほど読まれる。**書かれない ADR より、短い ADR の方がはるかによい。

| テンプレート | 目安 | いつ |
|:--|:--|:--|
| `brief` | **30 行以内** | 会話で決まった判断。既定を覆した記録。**既定はこれ** |
| `simple` | 60 行以内 | 落とした案が 1〜2 個あり、実装計画が要る |
| `madr` | 上限なし | 本当の選択肢が 3 つ以上あり、比較そのものを残したい |

`simple` / `madr` は、**その長さを判断が実際に要求しているとき**にだけ使う。
迷ったら `brief` で書き始める。後から広げるのは簡単で、逆は起きない。

## 作成の流れ

判断の大きさに合わせる。**`brief` に 4 フェーズは要らない。**

### `brief` の場合

会話に答えは出揃っている。**下書きを出して、直してもらう。**

```bash
make adr TITLE="Edit an existing migration instead of adding one"
```

埋まらない欄があるときだけ訊く。多くは「いつ見直すか」が残る。

### `simple` / `madr` の場合

#### フェーズ 0: リポジトリを読む

1. **既存 ADR と索引**（`docs/decisions/`）。関連する判断、置き換えることになる判断
2. **方向性メモ**（`docs/design/`）。特に「今回は扱わないもの」の節は、
   その論点が**意図的に先送りされたもの**かどうかを教えてくれる
3. **規約**（`server/AGENTS.md` §11 §13 §17、`ui/web/AGENTS.md`、`infra/*/AGENTS.md`）
4. **関係するコード。**判断が触る領域の実装と、既にある型

#### フェーズ 1: 意図を捉える

**一度に 1 問ずつ**訊く。質問リストを丸ごと投げない。フェーズ 0 で分かったことは飛ばす。

1. **何を決めるのか** — 動詞句にする（「X を採用する」「Y を Z に置き換える」）
2. **なぜ今か** — 何が壊れたか、放置すると何が壊れるか
3. **制約は何か** — フェーズ 0 で見たものを当てる
   （「`service_accounts` が既に主体の形を決めていますが、制約になりますか」）
4. **どの選択肢を検討したか** — 最低 2 つ。1 つしか無いなら、なぜ他が落ちたのかを一緒に言語化する
5. **明示的にやらないことは何か** — 非目標
6. **エージェントが実装するのに何が要るか** — どのファイル、どの既存の型に倣うか、
   何を避けるか、どのテストで確かめるか

**やめどき**: 全節をでっち上げずに埋められるようになったら。推測しているならまだ訊く。

**関門**: 題 / きっかけ / 制約 / 選択肢 / 傾き / 非目標 / 関連するもの / 影響範囲 / 検証
を要約して提示し、**確認が取れるまで起草に進まない。**

#### フェーズ 2: 起草する

```bash
make adr TITLE="Choose an agent runtime" TEMPLATE=simple   # または madr
```

プレースホルダを残さない。任意の節は、使わないなら消す。
**検証は実際に走るコマンドで書く**（`make test` / `golangci-lint run ./...` /
`pnpm test` / `migrate up`）。

#### フェーズ 3: チェックリストで見直す

`references/review-checklist.md` に照らす。**生のチェックリストを貼らず、要約で示す。**

> ✅ **問題なし**: {堅い点}
> ⚠️ **不足**: {具体的な不足}
> **判断**: {出せる / 先に埋める / フェーズ 1 に戻る}

指摘だけでなく直し方を提案する。通るか、人が明示的に不足を受け入れるまで確定しない。

## ADR を参照する

ADR がある領域に手を入れる前に読む。作成フローとは独立した操作である。

1. `docs/decisions/` と索引を見る。`accepted` が生きている判断
2. 題だけでなく、文脈・判断・帰結・非目標・**実装計画**まで読む
3. **判断を尊重する。**`accepted` に反することをするなら、それを置き換える新しい ADR が要る。
   コードと ADR が食い違っていたら人に報告する
4. PR とコードコメントから参照する（下記）

## コードと ADR の相互リンク

実装計画には実在のパスと実在の型を書く。コード側は、その判断に導かれた場所の
**入り口に 1 か所だけ**コメントを置く。行ごとには書かない。

```go
// 委譲は DB の行であってトークンではない。認可経路を 2 本にしないための判断。
// ADR: docs/decisions/2026-09-10-delegation-as-a-database-fact.md
type Delegation struct {
```

```typescript
// 生の HTML は描画しない。rehype-raw を足さないことが、この判断の本体。
// ADR: docs/decisions/2026-09-12-never-render-raw-html-in-markdown.md
```

## その他の操作

### 既存 ADR の更新

- **受理 / 却下 / 非推奨化**: `make adr-status ADR=<path> STATUS=<status>`。
  非推奨化のときは代替の経路を書く
- **置き換え**: 新しい ADR を作り、**双方向にリンク**する（旧 → 新、新 → 旧）
- **学びの追記**: `## 補足` に日付付きで足す。**過去を書き換えない**

### 受理後

1. 実装計画と帰結の項目をタスクにする（`docs/tasks/` か Issue）
2. PR 本文から ADR のパスを参照する（`create-pr` skill の「変更の背景と解決策」）
3. コードに参照コメントを置く
4. 検証項目を走らせ、結果を `## 補足` に日付付きで残す
5. 「いつ見直すか」に書いた条件を監視する

### 立ち上げ

`docs/decisions/` がまだ無いとき: `make adr-init`
