# 記入例

hub の実際の判断で書いた 3 例。**そのままコピーせず、書き方の水準を見る。**

共通しているのは、判断が「何を選んだか」ではなく
**「なぜ素直な方を選ばなかったか」**を中心に書かれている点である。

領域も意図的に散らしてある（会話で決まったもの / web / server）。
ADR が `server/` の認可の話ばかりになるなら、それは記録の偏りであって、
判断が偏っているわけではない。

---

## 例 1: brief — 会話で決まった判断

**最も取り逃がしやすい種類。**人の一言で決着し、コードには痕跡が残らず、
次に来たエージェントが「なぜ ALTER でないのか」を再発見する羽目になる。

```markdown
---
status: accepted
date: 2026-09-04
decision-makers: linzhengen
---

# Edit an existing migration instead of adding one

## 何が既定だったか

スキーマを変えるときは新しいマイグレーションを足す。
デプロイ済みのデータベースを壊さないための、ごく一般的な作法である。
実際、`organizations` の導入も当初は `000015`（新規テーブル）と
`000016`（`ALTER TABLE ... ADD COLUMN` + backfill）の 2 本で書かれていた。

## 何をどう決めたか

**既存のマイグレーションを直してよい。**hub はまだどこにもデプロイされておらず、
守るべき本番データベースが存在しない。守るものが無い前提を守り続けると、
スキーマの定義がマイグレーションの履歴に散らばり、
「この列は何のためにあるのか」がテーブル定義から読めなくなる。

先例がある。`user_groups.expires_at` は `ALTER` ではなく `000003` の
`CREATE TABLE` に直接書かれている。今回それを規約として認めた。

結果として `000015` / `000016` は消え、`organizations` は `000002` に同居し、
`ALTER` と backfill が丸ごと不要になった。

## 何が変わるか

- `server/db/migrations/postgres/` — 列の追加は原則、その表の `CREATE TABLE` を直す
- `golang-migrate` は版番号しか見ないので、タイトル部分のリネームは既存 DB に影響しない
  （`000002_create_table_groups` → `000002_create_table_organizations_and_groups`）
- 直したら **`down -all` → `up` の往復**を必ず確認する。
  up にトリガを足して down に `DROP TRIGGER` を書き忘れる事故が実際に起きた

## いつ見直すか

**本番にデプロイされたデータベースができた時点で、この判断は失効する。**
そのときは新規マイグレーションに戻す。
```

**なぜこれが ADR に値するか**: 「何が既定だったか」が埋まっている。
一般的な作法を、この repo の事情で意図的に覆している。
逆に、ここが埋まらない判断は ADR に値しない —— 既定どおりのことをしただけである。

## 例 2: simple — ui/web の判断

安全側の既定を「足さないこと」で守っている型。
`escalation` リストと同じ発想が web 側に現れたもの。

```markdown
---
status: accepted
date: 2026-09-12
decision-makers: linzhengen
---

# Never render raw HTML in the assistant's Markdown

## 文脈と課題

アシスタントの回答は Markdown で返り、`src/components/common/Markdown.tsx` が描画する。
サイト上で Markdown を描画しているのはここだけである。

問題は入力の出どころにある。回答はツール結果から組み立てられ、
ツール結果にはグループの説明・リソースのメタデータ・ユーザー名といった
**他の利用者が書いた文字列**が混ざる。それがそのまま描画経路に乗る。

`react-markdown` は既定では HTML をノードとして解析しない。
解析させるには `rehype-raw` を明示的に足す必要がある。

## 判断

**`rehype-raw` を足さない。**生の HTML を描画する経路そのものを作らない。

サニタイザを正しく設定するのではなく、**サニタイザが要る状態にしない。**
設定を間違える余地が無い方が、正しく設定されている状態より強い。

あわせて、**Markdown として描画するのはアシスタントの発言だけ**とする。
利用者の入力は字面どおりのテキストであり、解析するとアンダースコアが食われ、
改行が畳まれる。

### 非目標

- サイトの他の場所に Markdown を導入しない。描画経路は 1 つに保つ
- 数式・図表などの拡張は扱わない。必要になったら改めて判断する

## 帰結

- 良い点: HTML インジェクションの経路が存在しない。サニタイザの設定ミスが起こりえない
- 悪い点: アシスタントが HTML で表現したいものを表現できない。
  今のところ表形式は GFM で足りている
- どちらでもない点: Chat ルートは遅延読み込みなので、
  この依存は初期バンドルではなく Chat チャンク（約 53 kB gzip）に入る

## 実装計画

- **影響範囲**: `ui/web/src/components/common/Markdown.tsx`,
  `ui/web/src/components/common/Markdown.test.tsx`
- **依存**: `react-markdown` + `remark-gfm`。**`rehype-raw` は足さない**
- **倣う型**: スタイルは `components` prop で当てる。
  1 コンポーネントのために typography プラグインを足さない
- **避けること**: `rehype-raw` の追加。
  「一時的に」でも足さない —— 外すのを忘れた瞬間に経路が開く
- **移行**: 不要

### 検証

- [ ] `pnpm test` が通る
- [ ] `Markdown.test.tsx` が、HTML を含む入力を**文字列として**描画することを確かめている
- [ ] `package.json` に `rehype-raw` が現れない

## 却下した案

- **`rehype-raw` + `rehype-sanitize`**: 一般的な組み合わせだが、
  許可リストの設定を間違える余地が残る。ここでの入力は他人が書いた文字列なので、
  設定ミスの代償が大きい。
- **サーバー側で HTML を除去する**: 描画側が安全であることの保証にならない。
  安全性が 2 か所に分かれ、片方が緩めば意味を失う。

## 補足

- `ui/web/AGENTS.md` の Markdown 節が、この判断の要約を持つ
- 再考の引き金: アシスタントが HTML でしか表現できない出力を必要としたとき
```

## 例 3: madr — server の判断（抜粋）

選択肢が 3 つ以上あるときの形。文脈・実装計画・検証は例 2 と同じ水準で書く。

```markdown
# Hold a permission within an organization

## 文脈と課題

`Enforce` は `(resource, action)` のワイルドカード一致しか見ない。
「グループ X の管理者は X のメンバーだけ操作できる」が表現できず、
管理者は全能かゼロかの二択になる（`docs/design/iga-direction.md` の「穴 1」）。

## 判断の軸

- 既存の付与の意味を変えないこと（単一テナント運用が壊れない）
- キャッシュの不変条件を壊さないこと
- 規則が 1 か所にだけ書かれること

## 検討した選択肢

- A: 既存の group ツリーをテナント境界に流用する
- B: `organizations` を第一級で導入し、group が属する
- C: 権限文字列にスコープを埋め込む（`org:X/api.*`）

## 結論

**B**。境界を持つのは group である —— group が user と permission をつなぐ
唯一の辺だからで、そこに組織を置けば、通る経路すべてが組織を通る。

### 帰結

- 良い点: PLATFORM の付与が全組織に届くので、移行が既存の判定を 1 つも変えない
- 悪い点: `Enforce` の署名が変わる。呼び出し側すべてに影響する
- どちらでもない点: 組織を指定しないリクエストは従来どおりの意味になる。
  互換のためだが、絞り込みは呼び出し側が明示したときだけ効くということでもある

## 実装計画

- **倣う型**: 期限（`ExpiresAt`）とまったく同じ。SQL でフィルタせず、
  `grant.reaches` が判定時に落とす
- **避けること**: ポリシークエリに `org_id = $n` を足さないこと。
  キャッシュが「判定結果」を持つことになり、`rbac_revisions` が防いでいる失敗に戻る

### 検証

- [ ] 移行前後で既存ユーザーの `Explain` 結果が一致する
- [ ] 「全組織に届く」規則が `Kind.AppliesEverywhere` 1 か所にしか書かれていない

## 各選択肢の長所と短所

### A: group ツリーの流用

- 良い点: スキーマ変更が最小
- 悪い点: group が「所属」と「テナント」の二重の意味を持ち、スコープ判定が曖昧になる

### C: 権限文字列へのスコープ埋め込み

- 良い点: `Enforce` の署名が変わらない
- 悪い点: ワイルドカード規則と干渉する。「この人はどの組織にいるか」に答えられない
```

## この 3 例から読み取ること

- **文脈が、解決策ではなく問題を書いている**
- **却下した案に藁人形が無い。**どれも本当に成立しうる案で、
  落とした理由がこのリポジトリの既存の判断に紐づいている
- **実装計画が実在のパスと実在の型を指している**
- **検証が走るコマンドで書かれ、構造の検証も入っている**
- **悪い点が書かれている。**良い点しか無い ADR は、まだ考え切れていない
- **`brief` でも十分に判断が伝わる。**長さは価値ではない
