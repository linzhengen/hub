# ADR レビューチェックリスト

フェーズ 3 で使う。判定の基準はひとつ:
**エージェントがこの ADR を読んで、何も質問せずに実装を始められるか。**

## 文脈と課題

- [ ] 前提を持たない読者が、なぜこの判断が要るのかを理解できる
- [ ] きっかけが書かれている（何が壊れたか、何が変わるか、放置すると何が壊れるか）
- [ ] 暗黙知に依存していない。略語は定義され、システムは名前で呼ばれている
- [ ] 関連する Issue / PR / 既存 ADR / 方向性メモにリンクしている
- [ ] `docs/design/` の「今回は扱わないもの」に入っている論点なら、そのことに触れている

## 判断

- [ ] 実行できるだけ具体的（「もっと良い方法にする」ではなく「Y のために X を使う」）
- [ ] 範囲が閉じている。**やらないこと（非目標）が書かれている**
- [ ] 制約が具体的で、可能なら測れる形になっている

## 帰結

- [ ] 各項目が具体的で、実行可能。願望ではない
- [ ] 後続作業が特定されている（マイグレーション、設定、ドキュメント、テスト）
- [ ] リスクが、緩和策か「受け入れる理由」とセットで書かれている
- [ ] **良い点しか無い帰結になっていない。**何が高くつくのかが書かれている
- [ ] 判断の言い換えになっている項目が無い

## 実装計画

- [ ] 影響するファイル・ディレクトリが実在のパスで書かれている
      （「データ層」ではなく `server/internal/domain/auth/`）
- [ ] 依存の追加・削除・更新がバージョンとともに書かれている
- [ ] 倣うべき型が、実在のコードを指している（抽象的な説明ではない）
- [ ] 避けるべきことが書かれている
- [ ] 設定の変更（環境変数、`config/config.go`、Helm values）が挙がっている
- [ ] 置き換えなら、移行手順が書かれている

## 検証

- [ ] チェックボックスで書かれている（散文ではない）
- [ ] 各項目が**実際に走るコマンド**か、目視で確認できる具体的な状態
- [ ] 「動く」（機能）と「正しく作られている」（構造）の両方を見ている
- [ ] 曖昧な項目が無い（「性能が良い」→「p95 < 200ms」）

## 選択肢（MADR テンプレートのとき）

- [ ] 本当に検討した選択肢が 2 つ以上ある（「やる」対「やらない」ではない）
- [ ] 各案に長所と短所の**両方**がある。藁人形になっていない
- [ ] 採った案の理由が、判断の軸を指している
- [ ] 落とした案は「何か」ではなく「**なぜ落としたか**」が書かれている

## hub 共通

- [ ] **その規則がコードのどこに 1 か所だけ落ちるかが書かれている。**
      2 か所に書かれる規則は、2 か所で食い違う
- [ ] 生成物を手で直していない。手で直すなら、なぜそれが必要かが書かれている
- [ ] 検証に実際に走るコマンドが入っている

`brief` テンプレートのときは、ここまでで足りる。以下は触れた領域のものだけ見る。

## server / 認可に触れるなら

- [ ] proto を単一の出所として保っている。REST パスやパーミッションを手で書いていない
- [ ] 認可判定が読むテーブルを足すなら、`rbac_revisions` トリガに触れている
- [ ] 「キャッシュはポリシーの集合を持ち、判定結果は持たない」を壊していない
- [ ] 認証経路・認可経路を 2 本にしていない
- [ ] `escalation` / `exposed` / `audited` / `notAudited` を変えるなら、その理由が書かれている
- [ ] マイグレーションを足すか既存を直すかを明示している
- [ ] 検証に `make test` / `golangci-lint run ./...` / `make gen` の差分確認が入っている

## ui/web に触れるなら

- [ ] REST パスとクエリ文字列が `src/api/operations.ts` 経由になっている
- [ ] `Markdown.tsx` の安全側の既定を緩めていない（`rehype-raw` を足していない）。
      緩めるなら、ツール結果に他人の書いた文字列が混ざる前提でその安全性が論じられている
- [ ] React Compiler のルールを緩めて違反を黙らせていない
- [ ] UI ライブラリを増やすなら、既に Ant Design と Shadcn が同居している事実に触れている
- [ ] 資格情報に準ずるものを `localStorage` に置いていない。置くなら理由が書かれている
- [ ] 検証に `pnpm lint` / `pnpm lint:eslint` / `pnpm test` が入っている

## infra / リリースに触れるなら

- [ ] クラウドプロバイダを増やすなら、Terraform state の置き場をどうするかが書かれている
      （現状 backend は `local {}`）
- [ ] 依存・チャート・ベースイメージを足すなら、バージョンが固定されている
- [ ] 秘密がリポジトリに入らない形になっている

## ドキュメントに触れるなら

- [ ] 公開するかどうかが意識されている（`docs/site/` に入れるか否か）
- [ ] 生成されるページ（API 説明・API リファレンス）を手で書き写していない

## メタ

- [ ] status が正しい（新規なら普通は `proposed`）
- [ ] `date` が入っている
- [ ] `decision-makers` が入っている
- [ ] 題が、問題ではなく**決めたこと**を表す動詞句になっている
- [ ] ファイル名が `YYYY-MM-DD-english-slug.md`、本文が日本語

## 目安

チェックの数はゲートではなく、会話の道具として使う。

- **全部埋まった**: 出す
- **1〜3 個空き**: 人と話す。たいていすぐ埋まる
- **4 個以上空き**: フェーズ 1 に戻る。曖昧な領域が残っている

## よくある壊れ方

| 症状 | 原因 | 直し方 |
|:--|:--|:--|
| 帰結が「性能が上がる」 | 意図が曖昧 | 「どの指標が、どれだけ、どう測って」と訊く |
| 選択肢が 1 つ | 判断済みで、ADR が事後 | 「何を落としましたか、なぜ」と訊く |
| 文脈が解決策の売り込み | 問題を書いていない | 文脈を問題として書き直し、解を判断に移す |
| 帰結が良い点だけ | 都合の良いところだけ見ている | 「何が高くつきますか」と訊く |
| 「X を使う」だけで理由が無い | 比較していない | 「なぜ Y ではなく X か」と訊く。「Y ではなく」が比較を強制する |
| 実装計画が「コードを直す」 | 抽象的すぎる | 「どのファイルの、どの関数を、どの型に倣って」と訊く |
| 検証が「動くこと」 | テストできない | 「動くことを示すコマンドは何ですか」と訊く |
| 規則の落ちる先が書かれていない | 判断がまだ具体的でない | 「この規則はコードのどこに 1 か所だけ書かれますか」と訊く |
