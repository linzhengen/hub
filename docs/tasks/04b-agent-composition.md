# 4b. Agent の構成

## 目的

Agent に「どの MCP サーバー・どの Skill・どのサブ Agent を持つか」を紐付ける。

## なぜ

ここが二重ゲートの前半で、RBAC + 委譲チェーンが後半。両方を通らないと実行されない。
これは既存の `ToolBox.Tools()` / `Call()` の二重チェック
（一覧は提案を防ぎ、`Call` の中の検査が実際に効く）の Agent 版である。

この分離があるので、**Agent ごとの RBAC インスタンススコープは要らない**。
組織スコープと構成の許可リストで足りる。

## 先に決めること: 共有されるサブ Agent

**A2A には親子という概念が無い。**A2A が定義するのは Client Agent → Remote Agent の
呼び出しだけで、「エージェントが自分のサブエージェントとどう話すか」は仕様の外である。
木構造は ADK 側の概念で、そちらは **親が必ず 1 つ**（`LlmAgent.__init__` が
`Agent {name} already has a parent agent` で拒否する）。

したがって hub の `agents.parent_agent_id`（単一列）は **ADK 側の所有・系譜**であって、
呼び出し関係ではない。呼び出し関係は `delegations` の辺で、そちらは最初から多対多である。

決めるのは「1 つの翻訳 Agent を 3 つのオーケストレータが使う」をどう表すか:

- **A. 構成ごとに別の Agent 行**（＝別の識別子・別の資格情報）。ADK を素直に写した形で、
  「per-agent identity、資格情報を複数のワークロードで共有しない」という推奨にも沿う。
- **B. 1 行を共有し、親を多対多にする。**行は減るが、資格情報が 2 つの構成にまたがり、
  監査で「どちらの構成として動いたか」が消える。

**A を推す。**B を採るなら `parent_agent_id` を結合テーブルに置き換えることになるので、
この判断は結合テーブルを設計する前に済ませる。

> **単一列のまま `AddSubAgentsToAgent` を作ると、2 人目の親への追加は
> 「追加」ではなく「移動」になる。**A を採るなら、既に親を持つ Agent の追加は
> ADK と同じく明示的に拒否すること。黙って親が入れ替わるのが最悪である。

## やること

- 結合テーブル: `agent_mcp_servers`, `agent_skills`, および
  `agents.parent_agent_id` を使ったサブ Agent の紐付け。
- rpc は §17 の規約どおり `Add<Children>To<Parent>` /
  `Remove<Children>From<Parent>` の 2 本ずつ。「まるごと置換」は作らない。
- 構成にバージョンを持たせる（`agent_versions`）。5a のデプロイ単位になる。
- サブ Agent の循環を拒否する。親子は木であって、グラフではない。
  **循環が今できないのは、`parent_agent_id` を書き換える経路が無いからにすぎない**
  （`UpdateAgent` rpc は存在せず、親は Create 時にしか設定できない）。
  このタスクが `Add`/`Remove` を足した瞬間にその保証は消えるので、
  検査は rpc と同じ変更に入れること。

## 完了条件

- Agent に道具を付け外しでき、構成がバージョンとして固まる。
- 他組織の MCP サーバー / Skill を紐付けられない。
- 循環するサブ Agent 構成が作れない。
- 既に親を持つ Agent を別の親に付けようとしたとき、黙って移動しない
  （A を採った場合）。
