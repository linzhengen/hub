# 設計メモ: 権限台帳（一元化のコンセプト）

2026-08 / 対象: `server`, `ui/web`
前提: [`iga-direction.md`](./iga-direction.md)（穴 2 と穴 3 はここで埋まっている）

このメモは公開サイトには含まれない（`docs/build.mjs` は `docs/site/` だけを読む）。

## 1. 「一元化」は 3 つの別のプロダクトを指す

「すべての権限管理を一元化する」という言葉は、少なくとも 3 つの異なるものを指しうる。
どれを選ぶかで作るものが根本的に変わるので、最初に割る。

| | 何を一元化するか | hub の役割 |
|:--|:--|:--|
| (1) | 自前アプリの認可 | hub の API を守る。これまでの姿 |
| (2) | **台帳** — 誰がどのシステムに何を持っているか | 収集・申請・承認・棚卸し・監査の中心 |
| (3) | **実行時の判定** | 他システムが毎リクエスト問い合わせる PDP |

**(2) を採る。(3) はやらないと明示的に決める。**

(2) は「遅くてよい、正確で追跡可能であればよい」世界で、日次同期と承認フローが主役である。
(3) は「1ms で答える、落ちたら全システムが止まる」世界で、申請も承認も棚卸しも要らない。
要求が正反対なので、一つのシステムで両方やると片方が必ず歪む。

(3) を明示的に捨てるのは、決めないと「そのうち各アプリから実行時に問い合わせられるように
するかもしれない」という前提が設計に残り続け、可用性とレイテンシの要求が申請承認フローの
設計を歪めるからである。捨てた記録として残す。

### なぜ (2) か

hub が既に持っているものを並べると、答えは追認に近い。

- 期限付き付与（`expires_at`）
- 申請 → 別人の承認 → 付与、自己承認の禁止
- 全変更の監査ログ（channel・session・申請 ID 紐付き）
- explain（なぜこの人はこれができるのか / 誰がこれをできるか）
- サービスアカウント
- AI は起票できるが承認できない、という非対称性

これはすべて IGA の語彙である。実行時 PDP に申請フローも承認も棚卸しも要らない。
`iga-direction.md` で B+C を選んだ時点で、hub は台帳型に舵を切っていた。

## 2. 一番の落とし穴 —— 接続先の数で戦わない

台帳型を選んだ瞬間に現れる失敗の形は「全部のシステムに繋ぐ」を目標にすることである。
既存の IGA 製品が数百のコネクタを持っているのは 10 年以上かけたからで、
コネクタの数が勝敗を決める土俵に乗った時点で結果は決まっている。

したがって掲げるのは **接続先の数ではなく、接続の形を 1 つに決めること**。

- 収集コネクタのインタフェースは 1 本。「このシステムで、誰が、何を持っているか」を返すだけ。
- 最初の実装は特定 SaaS 用のコードを書かない。**SCIM と、素の HTTP / CSV 取り込み**の 2 本。
- 個別 SaaS は利用者が書く。hub は形を提供する。

**書き戻し（プロビジョニング）は第一段階では作らない。** 読み取りだけでも台帳の価値の
大半は出る。「承認していない権限が実在する」を言えることが台帳の存在価値であり、
それは収集だけで実現できる。

## 3. モデル

三層に分ける。

```
意図 (intended)    hub のグラフが言っていること = 承認された状態
     ↓ 突き合わせ
名寄せ (identity)  hub の user ↔ 外部システムのアカウント
     ↓
実態 (observed)    収集した結果、実システムにある状態
```

**ドリフト = 意図と実態の差**であり、名寄せを経由して突き合わせる。

- 実態にあって意図に無い → **未承認の権限**。台帳が存在する最大の理由。
- 意図にあって実態に無い → 未反映。書き戻しが無い第一段階では正常な状態でもある。
- どの hub ユーザーにも名寄せできない外部アカウント → **孤児アカウント**。
  退職者の残存アカウントや、誰のものか分からない管理者アカウントがここに落ちる。
  収集の出力として最も価値が高いのはおそらくこれで、名寄せ表があれば副産物として出る。

### 3.1 意図 —— 既存のグラフをそのまま使う

`resources` に 2 つの型を足す。

| type | 意味 | identifier の例 |
|:--|:--|:--|
| `menu` | 画面（既存） | `menu.system.users` |
| `api` | hub の rpc（既存） | `api.system.user.v1.UserService` |
| **`system`** | 外部システム | `system.github` |
| **`entitlement`** | そのシステムの中の権限 | `system.github.org:linzhengen:admin` |

`entitlement` は `parent_id` で `system` にぶら下がる。階層は既にある。

これで **新しい付与の仕組みを一切作らずに済む**。`permissions` は `(verb, resource_id)` なので、
entitlement を resource にすれば「GitHub org の admin」が permission になり、
role → group → user という既存の経路で付与できる。結果として:

- 期限付き付与（`expires_at`）がそのまま効く
- アクセス申請・承認がそのまま効く
- 監査ログがそのまま効く
- `ExplainUserAccess` が「なぜこの人は GitHub の admin なのか」に答える

台帳のために作るべき新しい機構は、意図の側には無い。

> **`Enforce` と台帳は同じグラフを読むが、別の問いである**
>
> `Enforce` は「この呼び出しを通してよいか」を訊く。ワイルドカードが効く問いで、
> `*` を持つ role は何にでも一致する。それは hub の中では正しい。
>
> 台帳の問い —— 「この人が持っているべき外部権限は何か」 —— でワイルドカードを
> 展開してはいけない。hub の全能管理者が GitHub の admin であるとは限らないし、
> `*` を「すべての外部権限を持つ」と読むと、ドリフト検出が全システムで
> 偽陰性になる（意図側が何にでも一致するので、未承認の権限が検出されない）。
>
> したがって台帳側は `Enforce` を経由せず、**明示的に紐づいた entitlement だけを
> 返す専用のクエリ**を持つ。`IntendedEntitlements(userId)` はワイルドカードを展開しない。
> 同じグラフを 2 つの問いに使うが、ワイルドカードの扱いが違う。

`api` / `menu` と `system` / `entitlement` のもう一つの違いは、**hub が enforce するか
どうか**である。`api` は hub が実際に許可を判断する。`entitlement` は hub は判断しない
—— 実態は外部システムにある。hub が記録しているのは意図だけである。
この区別を型で表現しておかないと、「hub のグラフにある」を「実システムで有効」と
読む人が必ず出る。

識別子の名前空間が分かれている（`api.*` / `system.*`）ので、
`Enforce` の一致で両者が衝突することはない。SQL に型のフィルタは足さない。

### 3.2 名寄せ

```
external_accounts
  id
  user_id            NULL 可 —— NULL が孤児アカウント
  system_resource_id 外部システム（resources の system 行）
  external_id        システム内の不変 ID
  external_username  表示用。変わりうる
  linked_by          MANUAL | EMAIL | SCIM
  linked_at
  last_seen_at       最後に収集で見えた時刻
  UNIQUE (system_resource_id, external_id)
```

`user_id` が NULL 可であることがこの表の要点である。収集は名寄せできないアカウントも
記録しなければならない。名寄せできなかったという事実そのものが成果物だからである。

第一段階の自動名寄せはメールアドレス一致のみ。手動で結び直せること、
そして「結び直した」が監査に残ることのほうが、賢い自動一致より重要である。

### 3.3 実態

```
observed_entitlements
  external_account_id
  entitlement_resource_id
  first_seen_at
  last_seen_at
  PRIMARY KEY (external_account_id, entitlement_resource_id)
```

収集は**全置換ではなく last_seen_at の更新**にする。全置換だと、収集が部分的に
失敗したときに「無くなった」と「見えなかった」が区別できない。
`last_seen_at` が古い行は「前回の収集で見えなかった」であって、
「失効した」ではない。この区別を消してはいけない。

> **rbac_revisions のトリガは足さない**
>
> `observed_entitlements` と `external_accounts` は認可の判断に使わない。
> 判断に使うのは意図の側（`resources` / `permissions` / `role_permissions`）だけで、
> そちらには既にトリガがある。収集は定期的に大量の行を書くので、
> ここにトリガを足すと収集のたびにポリシーキャッシュが全消しになる。
>
> `AGENTS.md` の「認可の判断が読む新しい表にはトリガが要る」の裏返しであり、
> **判断が読まない表にはトリガを足してはいけない**。

### 3.4 hub 自身を最初のシステムにする

台帳になるなら、hub の中の権限も「hub というシステムの権限」として台帳に並ぶべきで、
**hub 自身が最初のコネクタになる**。

これは対称性の趣味ではなく設計の検証である。hub 自身を自分の台帳に載せられない
モデルは、他のシステムも載せられない。hub のコネクタは外部 API を叩かず
自分のグラフを読むだけなので、収集の形が正しいかどうかを、ネットワークも
認証情報も無しに確かめられる。

## 5. 今回は扱わないもの

- **書き戻し（プロビジョニング）**: 読み取りで台帳の価値の大半が出る。
  書き戻しは失敗したときの整合性の議論が別途要る。
- **実行時 PDP**: §1 で明示的に捨てた。
- **穴 1（スコープ付き権限）**: 保留は変わらないが、**スコープの単位は「システム」に決まった**。
  「GitHub の権限だけ管理できる人」「本番 DB の棚卸しだけ担当する人」が単位になる。
  一元化を決める前に穴 1 を実装していたら単位を「グループ」に取り、
  台帳を載せた時点で作り直しになっていた。順序として、コンセプトが先で正しかった。
- **アクセスレビュー（棚卸しキャンペーン）**: 台帳と名寄せが入ってからでよい。
  レビューする対象も、レビューする人も、台帳が無いと決まらない。
