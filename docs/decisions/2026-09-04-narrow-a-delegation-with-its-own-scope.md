# Narrow a delegation with its own scope

## 何が既定だったか

`docs/design/agent-platform-direction.md` §4.2 が置いた定義はこうだった。

> Agent の実効権限 = Agent 自身の権限 ∩ 委譲元ユーザーの権限

そして §6「今回は扱わないもの」が、これ以上絞る仕組みを明示的に退けていた ——
構成の許可リストと組織スコープで足りる、三つ目を足すとどれが効いているか
説明できなくなる、と。

この二項の交差だと、**ユーザーは自分の権限を全部渡すか、何も渡さないかしか選べない。**
「この Agent には問い合わせの読み取りだけ任せる」が表現できない。

## 何をどう決めたか

**`delegations` に、その委譲自身を狭める列を持たせる。交差は三項になる。**

    Agent 自身の権限 ∩ 委譲元ユーザーの権限 ∩ その委譲のスコープ

§6 が退けたのは「Agent ごとの RBAC **インスタンス**スコープ」——
この Agent はこのリソースの**どの行**に触れてよいか、という別の軸である。
ここで足すのは委譲された権限そのものの絞り込みで、
**同じ `Enforce` の中で単調減少するだけ**だから、「権限を狭める仕組みが 2 つ並ぶ」に
はならない。OAuth の scope、A2A の「トークンをスキルにスコープする」、
Google の「実行時に、そのクエリに関係する権限だけを有効にする」は、
どれも同じことを別の言葉で言っている。

`NULL` は「委譲元の全権」を意味し、二項だった頃と同じ挙動になる。
狭い委譲が普通で、全権が例外である。

交差は**判定時**に取る。付与時に畳み込むと、あとで委譲元の権限が失われても
Agent が持ち続ける —— `expires_at` を SQL で落とさず `Enforce` が時刻で落とすのと
まったく同じ理由である。

## 何が変わるか

- `docs/tasks/03a-delegation-model.md` のマイグレーション
  `000016_create_table_delegations` に絞り込み列が加わる
- `docs/tasks/03b-delegation-enforcement.md` の
  「チェーン上の全員が許可されていること」に、
  「かつ、その委譲のスコープに含まれること」が加わる。
  判定は `auth.Service.Enforce` の 1 か所のまま
- `docs/design/agent-platform-direction.md` §4.2 の定義式と §6 の
  「今回は扱わないもの」を、この ADR に合わせて直す
- `Explain` も同じ規則を通る。答えと説明が食い違ってはいけない

## いつ見直すか

- 委譲のスコープを書く人が、書けずに全権を選び続けるようになったら。
  そのときは列ではなく、**書き方**（プリセット、Agent の構成からの導出）が
  足りていない
